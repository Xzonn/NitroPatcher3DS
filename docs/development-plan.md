# NitroPatcher3DS 开发方案

## 目标与运行流程

在安装了自制固件的 3DS／2DS 上，使用正版 NDS 卡带和现有 `.xzp` 汉化补丁运行游戏。游戏运行期间持续从原卡带读取原始内容，从 SD 卡读取修改后的内容，直接读写原卡带存档。汉化补丁按保持原有存档格式处理。

用户流程：插入卡带 → 选择 `.xzp` → 准备补丁缓存 → 启动游戏。已经准备好的相同组合直接复用缓存。

程序使用 C/C++、devkitARM 和 libnds，在 DS／DSi 模式运行，通过 CIA 安装到 HOME 菜单。准备程序和游戏运行引擎分别链接，启动游戏前释放准备阶段的内存。

## .xzp 处理

ZIP 使用 miniz，VCDIFF 使用 xdelta3，JSON 使用 cJSON，NDS 文件系统解析复用 ndstool 的现有实现。生成布局遵循 nitro-patcher 的 `NDSFile.toBuffer()`。

1. 按原始 ROM 的完整输入内容计算 MD5，处理 `md5.txt`。
2. 根据原始 MD5 选择 `preprocessing/<MD5>.xdelta`，在解析文件之前应用预处理。
3. 枚举已有系统文件、overlay、NitroFS 文件及没有文件名的 FAT 条目。
4. 对文件应用 `xdelta/<路径>` 或直接替换；差分优先。
5. 重新生成布局、文件分配表、overlay 信息及必要校验。
6. 将最终结果保存为地址映射和补丁数据。

ZIP 的路径大小写、分隔符、文件名编码及重复条目规则沿用 nitro-patcher。FNT 替换保持原有文件 ID；header.bin、banner、ARM9 尾部信息、Secure Area 和 DSi 数据处理与参考实现保持一致。格式支持范围以固定提交的 nitro-patcher 为准。

## 虚拟 ROM 与数据来源

| 类型  | 读取方式                         |
| ----- | -------------------------------- |
| CARD  | 从原卡带指定物理偏移读取         |
| PATCH | 从 SD 卡补丁数据文件指定偏移读取 |
| FILL  | 生成指定填充字节                 |

每条映射保存虚拟起点、长度、来源和来源偏移。映射按照虚拟地址排序并合并连续区间。内存保存分段索引，完整映射按需读取。

文件移动后，原样保留的内容仍映射到原卡带位置。整份 ROM 预处理和文件级差分均记录数据来源：源复制继承源映射，新增字节写入补丁数据，目标复制展开对应的来源映射并处理重叠复制。最终运行映射展开为 CARD、PATCH、FILL。

成熟格式的解析逻辑使用现有依赖。xdelta3 需要适配文件支持的窗口存储和输出来源记录，覆盖源窗口、目标窗口、重叠复制及窗口校验。ZIP 条目和临时数据逐项处理，内存使用固定大小的读写缓冲区。

真实卡带头和修改后的游戏头分别保存。卡带通信使用真实头中的芯片与加密参数，游戏加载使用修改后的布局。明确转换物理 Secure Area、补丁输入和内存加载表示。

## 持久缓存与失效规则

| 数据                   | 生命周期                       |
| ---------------------- | ------------------------------ |
| 解压及差分处理中间文件 | 准备过程中使用，成功后删除     |
| 地址映射和补丁数据     | 持久保存在 SD 卡，后续启动复用 |
| 游戏运行内存缓存       | 每次启动重新建立，退出后释放   |

缓存身份包括原始 ROM MD5、补丁文件内容摘要、缓存格式版本和生成规则版本。首次准备计算原始 ROM MD5；后续启动核对真实卡带的游戏编号、修订版本及头部信息。相同游戏版本的正版卡带可以共用缓存。

补丁内容摘要使用 SHA-256，随读取 `.xzp` 计算。补丁改名保持缓存有效，同名文件内容变化产生新的缓存身份。缓存不按使用时长过期。

缓存放在 `sd:/nitro-patcher/cache/<原始ROM-MD5>/<补丁SHA256>/`。准备过程使用该补丁目录内独立的 `pending/` 目录；文件全部完成并关闭后发布完成标记。启动器只接受格式版本匹配、文件完整且存在完成标记的结果。

启动时依次执行：核对卡带身份 → 识别补丁内容 → 查询缓存 → 复用有效结果或重新准备。卡带与补丁不匹配时终止启动。中断后残留的 pending 结果不能用于运行，重新准备前只清理对应的未完成目录。

补丁内容或生成规则变化时生成对应的新缓存。新结果完成后再清理同一游戏和补丁所替代的旧缓存，其他补丁缓存保持独立。清理范围始终限制在应用自己的缓存目录。存档操作不参与缓存有效性判断。

## 加载与运行引擎

启动和运行共用虚拟 ROM 读取接口，覆盖游戏头、ARM9、ARM7、适用时的 ARM9i/ARM7i、overlay、预加载资源、游戏内子程序、软复位和重新加载。

接入 ARM9 同步、异步和 DMA 读取，以及 ARM7 自身的读取路径。ARM7 协调实际卡带和 SD 卡访问；ARM9 使用 nds-bootstrap 的既有通信机制提交请求。跨映射请求拆分执行，完整请求完成后保留游戏原有的通知顺序。

内存缓存使用虚拟地址，底层卡带驱动使用映射后的物理地址。Slot-1 在游戏运行期间保持可用。引擎内存区域沿用 nds-bootstrap 的布局，新增占用必须与游戏程序、overlay 和共享内存逐项核对。

## 卡带存档

复用 nds-bootstrap 的 `SAVE_RELOCATION=0` 路径。原始卡带身份与补丁后的 gameCode 分开保存，存档身份判断使用原始身份。

保留游戏原有存档函数、写入完成语义和实际卡带通信。ROM 读取与存档事务协调使用卡带硬件；存档事务期间禁止复位卡带或抢占进行中的通信。启动、子程序重载和软复位均保留这一策略。游戏专用补丁中的存档处理也必须遵循该策略。

## 开发阶段与验收

| 阶段 | 实施内容                                         | 验收条件                                                                                         |
| ---- | ------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| 1    | 固定参考源码、构建入口、卡带信息和原卡带启动程序 | 生成 NDS 与 CIA；检查头信息、程序区间和打包结果；真机启动并读写原存档                            |
| 2    | .xzp 准备、布局、地址映射、持久缓存              | 真实 ROM 和现有补丁的完整映射读取逐字节等于 nitro-patcher 输出；缓存复用、失效、中断恢复符合规则 |
| 3    | 启动加载和 ARM9／ARM7 混合读取                   | 汉化程序、文本、字库、图片和 overlay 正确加载；运行期间实际读取原卡带                            |
| 4    | 异步读取、DMA、缓存、原卡带存档协调              | 连续运行、保存、重新启动及读取存档正常                                                           |
| 5    | 软复位、休眠、子程序和特殊硬件路径               | 相关游戏场景通过实际功能验证                                                                     |
| 6    | 安装包与端到端验收                               | 安装、选择现有补丁、首次准备、缓存复用、启动、保存、重新读取完整通过                             |

桌面验证使用真实 ROM 和实际 `.xzp`，以 nitro-patcher 输出作为参考，包含整份 ROM 预处理、文件扩容、程序和 overlay 修改、大资源替换、跨映射及非对齐读取。桌面端和掌机端共用映射逻辑。

真机调试构建记录实际驱动访问，确认 CARD 请求访问物理卡带。保存后通过原版游戏启动读取同一进度，确认数据写入卡带。测试前保留已有存档备份。构建、包结构检查、模拟器验证及真机功能验证分别记录。
